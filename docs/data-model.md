# GAP Data Model and Authorization

**Status:** Active
**Last updated:** 2026-10-21
**Source of truth for:** Database schema, relationships, statuses, RLS, and Storage contracts

## Conventions

- Use UUID primary keys generated by Postgres.
- Use `timestamptz` for timestamps and default audit timestamps to `now()`.
- Normalize roster/profile emails to lowercase and enforce uniqueness.
- Add foreign-key indexes and indexes used by RLS or frequent filters.
- Enable RLS on every table in an exposed schema.
- Use explicit `to authenticated` policies and `(select auth.uid())` where appropriate.
- Keep role lookup helpers in a non-exposed private schema and lock down function search
  paths.

## Enums

- `app_role`: `member | admin`
- `program_quarter`: `fall | winter | spring`
- `cohort_state`: `draft | active | archived`
- `participation_status`: `enrolled | completed | withdrew`
- `advancement_status`: `pending | promoted | not_promoted`
- `promotion_response`: `pending | joined | declined`
- `submission_type`: `file | link`
- `submission_status`: `submitted | revision_requested | completed`

Do not store `overdue`, `due_soon`, or `upcoming`; derive them from deadline and current
submission state.

## Tables

### Assignment PDF briefs

`public.assignment_documents` stores an immutable unique Storage path, assignment and
uploading Auth owner, original filename, size (1–20,971,520 bytes), creation/one-hour
expiry timestamps, expected prior document ID, `pending|ready|abandoned` state, and
`is_current`. A partial unique index permits one current document per assignment.
Assignment/owner/prior-document foreign keys restrict deletion to preserve references.
RLS allows live admins to read metadata; active enrolled members see only current ready
documents attached to published weeks in an authorized cohort. Ordinary clients have
no metadata write grants.

Private `assignment-briefs` Storage allows PDF only, 20 MB maximum. INSERT requires
the exact unexpired pending path owned by a current admin. SELECT requires a ready
document and current admin or published/current/cohort authority. No client overwrite
or delete policy is granted. Paths are generated by the server under owner/assignment.

Service-only `assignment_brief` repeats live admin authorization using the verified
server actor. Preparing records the current document ID. Finalization locks the
assignment before the upload row, compares the expected document, verifies Storage
metadata after server byte inspection, and atomically supersedes the previous brief.
Ready retries return the same receipt. Cancellation marks pending rows abandoned;
server cleanup never deletes ready/superseded documents. Unfinished objects may remain
after expiry or interrupted cancellation; scheduled cleanup is still pending.

`update_cohort_dates(uuid,date,date)` is an authenticated, live-admin-only function
that updates only `starts_on`/`ends_on` and rejects missing/inverted dates or IDs.
No browser role can bypass roster authorization by editing profile metadata.

Implementation boundary: committed migrations now include profiles, program content,
submissions, authenticated read policies, and authorized transactional mutation functions.
Local program authorization/concurrency and core browser checks pass; hosted and extended
Monday acceptance remain separate. P6 adds private Storage,
upload intents, file metadata, and service-only lifecycle operations.

Local program verification now additionally exercises direct non-upload Server Actions,
live role removal, session refresh/revocation, and explicit member query scoping. These
checks supplement rather than replace RLS: member-facing queries constrain person,
participation, active cohort, published weeks, and enrollment history even when the
caller is an admin. No schema or policy changes were required for this scoping update.
Extended Monday and hosted acceptance remain separate checks in `todo.md`.

Demo cohorts and participants are optional development fixtures, not required baseline
records. Local startup no longer seeds them automatically; an empty program with an
independently approved admin is valid. Keep real identities out of committed seeds.

### `people`

- `id uuid primary key`
- `email text unique not null`
- `full_name text not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

People are GAP participants or admins retained for historical reporting. This is not a
directory of the full club.

### `approved_members`

- `id uuid primary key`
- `person_id uuid unique not null references people(id) on delete restrict`
- `email text unique not null`
- `full_name text not null`
- `role app_role not null default 'member'`
- `active boolean not null default true`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

The roster is the authorization authority and may exist before first login. Deactivation
removes access without deleting the linked person or cohort history.

### `profiles`

- `id uuid primary key references auth.users(id) on delete cascade`
- `person_id uuid unique not null references people(id) on delete restrict`
- `email text unique not null`
- `full_name text not null`
- `role app_role not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

Profiles mirror the active roster entry for an authenticated user. Members cannot modify
their role.

### `program_cohorts`

- `id uuid primary key`
- `quarter program_quarter not null`
- `year smallint not null`
- `starts_on date not null`
- `ends_on date not null`
- `state cohort_state not null default 'draft'`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

Enforce one cohort per `(quarter, year)` and `ends_on >= starts_on`. Calendar-year labels
such as `Winter 2027` avoid ambiguous academic-year storage.

### `cohort_enrollments`

- `id uuid primary key`
- `cohort_id uuid not null references program_cohorts(id) on delete restrict`
- `person_id uuid not null references people(id) on delete restrict`
- `participation_status participation_status not null default 'enrolled'`
- `advancement_status advancement_status not null default 'pending'`
- `promotion_response promotion_response`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

Enforce one enrollment per `(cohort_id, person_id)`. A promotion response is required only
when advancement is `promoted` and must otherwise be null. Formal enrollments remain in
the starter denominator even if participation later becomes `withdrew`.

### `program_weeks`

- `id uuid primary key`
- `cohort_id uuid not null references program_cohorts(id) on delete restrict`
- `week_number smallint not null check (week_number between 1 and 6)`
- `title text not null`
- `description text not null`
- `published boolean not null default false`
- `slides_url text`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

Enforce unique `(cohort_id, week_number)` so every cohort may have its own six weeks.

### `resources`

- `id uuid primary key`
- `week_id uuid not null references program_weeks(id) on delete cascade`
- `title text not null`
- `description text`
- `resource_type text not null`
- `url text not null`
- `sort_order integer not null default 0`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

Order by `sort_order`, then `created_at` for deterministic rendering.

### `assignments`

- `id uuid primary key`
- `week_id uuid not null references program_weeks(id) on delete restrict`
- `title text not null`
- `instructions text not null`
- `due_at timestamptz not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

`week_id` is no longer unique. `sort_order integer not null default 1 check (>0)` and
the `(week_id,sort_order,id)` index define deterministic assignment order. Existing
assignment IDs, submissions and PDF metadata remain unchanged by the migration.

`save_program_week(jsonb)` is a live-admin-authorized function called from the existing
`admin_mutate('week', ...)` interface. It locks the week and its existing assignments,
validates an assignment array (up to 100 items), rejects duplicate/missing IDs and
cross-week reuse, and atomically saves the content, assignments, ordering and resources.
Missing assignments are deleted only when foreign-key history protections permit it;
a protected deletion rolls back the entire save. A stale editor snapshot cannot
silently erase a newly added sibling: the editor
sends `expectedAssignmentIds`, compared with the locked current collection. A mismatch
returns `40001` before any writes. An older single-assignment payload
remains supported only while the week has at most one assignment; otherwise it gets a
stale-save error rather than deleting the collection. Ordinary RLS policies and
per-assignment/enrollment uniqueness still govern submissions and upload operations.

### `submissions`

- `id uuid primary key`
- `assignment_id uuid not null references assignments(id) on delete restrict`
- `enrollment_id uuid not null references cohort_enrollments(id) on delete restrict`
- `submission_type submission_type not null`
- `original_filename text`
- `file_path text`
- `file_size bigint` (required for files; 1–20,971,520 bytes)
- `mime_type text` (required for files; null for links)
- `submitted_url text`
- `status submission_status not null default 'submitted'`
- `feedback text`
- `reviewed_by uuid references profiles(id) on delete set null`
- `reviewed_at timestamptz`
- `supersedes_submission_id uuid references submissions(id) on delete restrict`
- `is_current boolean not null default true`
- `submitted_at timestamptz not null`
- `updated_at timestamptz not null`

Constraints require the assignment week and enrollment to belong to the same cohort and
exactly one of `file_path` or `submitted_url` according to
`submission_type`. A partial unique index permits only one current submission per user
and assignment. Resubmission atomically sets the previous row to non-current and inserts
a new row pointing to it. Historical records are never silently overwritten.

## Safe week catalog

Members need week numbers/titles for locked draft cards without receiving draft content.
Expose a narrowly scoped authenticated function or security-invoker-safe contract that
returns only `week_number`, `title`, and `published`. Direct member SELECT policies on
`program_weeks`, resources, and assignments expose full rows only when published.

## RLS capability matrix

| Resource | Member | Admin |
| --- | --- | --- |
| Own profile and active enrollment | Read | Read all profiles/enrollments |
| People, roster, cohorts, outcomes | No direct access beyond own active context | Read/create/update; no hard delete required |
| Week catalog | Read safe fields | Read all |
| Published weeks/resources/assignments | Read | Read/write all |
| Draft content | No access | Read/write |
| Own submissions/history/feedback | Read and create; replace through authorized mutation | Read/write all |
| Other members' submissions | No access | Read/write |

Authority comes from `auth.uid()`, a confirmed UC Davis email with a Google identity in
Auth, and the current active approved roster joined to its person. Profiles are mirrors,
not authorization authorities; editable user metadata never grants roles. Member learning
requires enrolled participation in an active cohort. Direct authenticated table access is
read-only under RLS; writes use explicitly granted, role-checking functions with empty
search paths. Monday mappings have no authenticated read grant.

`submit_link` locks the enrollment and current attempt, checks the expected attempt ID
and update timestamp, rejects completed work, and supersedes/inserts atomically. It accepts
links only in P5. `admin_mutate` authorizes against the live roster before editing program
records or invoking private enrollment. `review_submission` returns the saved timestamp
inside the same transaction, so a later review cannot silently advance the caller's
optimistic-concurrency token. Missing/stale tokens fail closed. Resource rows currently
receive new IDs on a week save; they are not external identifiers.

## Cohort reporting

Admin summaries derive rather than store:

- `starters`: all cohort enrollments;
- `advancement_rate`: promoted divided by finalized advancement decisions;
- `offer_yield`: joined divided by finalized promoted responses;
- `end_to_end_conversion`: joined divided by all cohort starters.

Always show pending-decision, pending-response, and withdrawal counts with these rates so
their denominators remain clear.

## Monday reporting contract — Planned

Manual intake now uses the accepted-members board. The historical application-link
table name remains, but its triple identifies one member item/cohort participation.
`private.monday_import_batches` stores owner Auth ID, account/board IDs, trusted source
rows, mappings, results, and creation/15-minute expiry timestamps. RLS has no direct
browser or service table grants. Service-only `public.monday_import` stages, reads,
maps, and processes batches, rechecking live admin authority and ownership each time.
Per-row enrollment and receipt are atomic; batch locking serializes confirmations.
Expiry blocks processing but does not purge audit records; retention is not automated.

The [planned reporting set](product-spec.md#mondaycom-recruiting-and-club-reporting--planned)
is a projection of GAP records, not a second authoritative store. Monday remains the
source for applicants, recruiting decisions, and club-wide person records; do not
import all applicants into the GAP participant or access tables.

`private.monday_application_links` stores a UUID primary key, nonempty trimmed text
`account_id`, `board_id`, and `item_id`, an `enrollment_id` foreign key with delete
restriction, and `created_at`/`updated_at` timestamps. The external identifier triple is
unique; `enrollment_id` is indexed but not unique. Multiple applications can link to one
enrollment, while returning participants retain separate cohort enrollments. Person and
cohort are derived through the enrollment, not copied into the mapping. Manual enrollment
requires no external link. No rejected/unapproved applicant is imported by a live adapter.

The table is private, with RLS enabled and no browser grants. `service_role` may read links
but cannot directly insert/update/delete them; inserts go through the private operation.
Admin access will go through an authorized server boundary, not a client-side admin flag.
Actual Monday board/column configuration and live adapter remain pending.

The “Enroll in GAP” checkbox is enrollment intent, not an authorization field. Successful
processing links `people`, `cohort_enrollments`, and `approved_members` under the
[enrollment rules](product-spec.md#enrollment-approval--approved-not-implemented).
New access uses the member role; preserve existing roles and require explicit GAP admin
approval to reactivate previously deactivated access. Do not reset existing enrollment
outcomes on retries. The link creation timestamp records successful application linking;
it is not a pending-request log. Checkbox pending/failure reporting remains adapter work.

### Enrollment operation — Implemented, not connected to the portal

`private.enroll_in_gap(p_email text, p_full_name text, p_cohort_id uuid,
p_account_id text default null, p_board_id text default null, p_item_id text default null)`
returns one row: `person_id uuid`, `enrollment_id uuid`, and `created boolean` (whether the
enrollment itself was newly created, not whether a mapping was added).

Only `service_role` and the database owner can execute this private SQL function directly;
it is not an exposed PostgREST RPC. The authenticated admin mutation wrapper checks the
current roster role before invoking it. A future Monday caller must verify acceptance
and lead approval before invoking it. Caller-provided
claims cannot substitute for database execution privileges. It never trusts mock identity.

The transaction validates a nonempty name, normalized UC Davis email, existing cohort,
and all-or-none external identifiers. Existing application links are resolved first;
email/cohort mismatch requires manual resolution, never relinking. Without a mapping,
normalized email links an existing person. Existing names/roles/outcomes are not overwritten.
Previously inactive access and roster/person email conflicts fail closed.

All provisioning and optional linking occur atomically. A transaction-scoped advisory
lock serializes this low-volume operation, while unique constraints protect against other
writers. Replays return the same enrollment without timestamp/history resets. Failures
roll back all new rows. Any existing cohort is eligible (including draft/archived); retries
therefore remain valid after archival, and choosing the intended cohort is the caller's
responsibility. No unchecking/revocation behavior is implemented by this operation.

For per-person due-work reporting, count distinct published assignments whose deadlines
have passed at the report's as-of time. Count one current attempt per assignment:

- Submitted: due assignments with any current attempt, including revision-requested work.
- Approved: due assignments whose current attempt is `completed`.
- Awaiting review: due assignments whose current attempt is `submitted`.
- Outstanding revisions: due assignments whose current attempt is `revision_requested`.
- Missing: due assignments without a current attempt.

Report counts and the due-assignment denominator together. A zero denominator produces
“Not yet due”/an unavailable rate, not 0% or 100%. Historical attempts never inflate
these counts; future and draft assignments do not enter the denominator. This reporting
submission rate is distinct from the portal's module-completion calculation.
Cohort assignment rates aggregate these counts for currently enrolled participants;
report withdrawals separately. Existing starter-based outcome denominators above retain
withdrawn participants. Cohort completion is the participation status `completed`,
not an inference that every submitted assignment was approved.

## Storage

- Bucket: `submissions`
- Visibility: private
- Maximum object size: 20 MB
- Allowed types: PDF, DOCX, PPTX, XLSX MIME types
- Object path: `{user_id}/{assignment_id}/{submission_id}-{sanitized_filename}`
- Filenames are sanitized for paths while `original_filename` is stored for display.
- INSERT requires an exact pending, unexpired upload intent owned by `auth.uid()`,
  live active-roster authority, enrolled participation in an active cohort, and a
  published assignment. A path prefix alone never authorizes an upload.
- SELECT requires a committed submission associated with the live active owner or
  admin. This includes historical attempts regardless of current cohort participation.
  Uncommitted objects cannot be read by members or reviewers. No browser UPDATE or
  DELETE policy exists. Admins cannot upload on behalf of members.
- Replacement creates a new uniquely named object; old objects remain available with
  historical submissions.
- Downloads use `/api/submissions/[id]/download`, with current user-scoped RLS and
  private/no-store attachment streaming; the app does not generate signed or public URLs.

### Private upload ledger

`private.upload_intents` stores owner Auth UUID, assignment/enrollment, reserved unique
submission UUID, unique generated path, original filename, expected bytes/MIME,
expected current attempt ID/update timestamp, created/one-hour expiry timestamps,
state (`pending`, `committed`, `abandoned`), and cleanup timestamp/failure flag.
There are no direct anonymous/authenticated/service-role table grants.

Service-only `file_upload(actor, action, intent, data)` checks the verified actor's live
roster on every call. Prepare authorizes context and reserves the server-generated path;
get exposes only that actor's intent; cancel irreversibly abandons uncommitted work.
Only trusted server code may invoke finalize after bounded content inspection. It
locks intent → enrollment → current submission, rechecks authorization and the original
version, verifies Storage metadata, and atomically supersedes/inserts/commits. Link saves
use enrollment → current submission and reviews lock the current submission, so no
reverse intent dependency exists. Committed retries return the same receipt. Stale and
invalid finalizations abandon the intent without changing submission history.

`cleanup_uploads` is service-only. It locks and terminally abandons up to 100 expired or
abandoned intents, marks a cleanup attempt, and returns paths to the local Storage API
cleanup command. Optional owner scoping isolates test writes. Finalization cannot commit
a claimed path. Cleanup rechecks tombstones after five minutes, including successful
attempts, to remove late-finishing transfers; the ledger is not purged. Failure receipts
remain retryable. Committed intents and historical objects are never cleanup candidates.
The local command accepts an optional `--owner` Auth UUID to use that scope on every
claim/receipt; tests never run unrestricted cleanup. Each invocation is bounded to 100 batches.
See [ADR 0009](decisions/0009-private-upload-lifecycle.md).

## Migration rules

- Commit ordered SQL migrations and seed SQL; never rely on undocumented dashboard-only
  table changes.
- Make migrations safe for a fresh Supabase project and document any non-transactional
  manual step.
- Regenerate checked-in database TypeScript types after schema changes.
- Test policies as anonymous, member, admin, inactive roster member, and cross-user
  access before release.
